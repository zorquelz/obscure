1. Chapter 1: Chromium Multi-Process Architecture & Engine Internals

Chromium is designed as an operating system inside an operating system to prevent single-tab memory leaks and crashes from destabilizing the entire browser window. 

                            [ USER DESKTOP ]
                                   |
                                   v
             +-------------------------------------------+
             |         BROWSER PROCESS (Privileged)      |
             |  - UI Chrome (Tabs, Omnibox, Windows)     |
             |  - Network Sockets & Disk I/O             |
             |  - Storage (Cookies, History, DBs)        |
             +-------------------------------------------+
                     /             |             \
          Mojo IPC  /   Mojo IPC   |   Mojo IPC   \  Mojo IPC
                   /               |               \
                  v                v                v
     +-----------------+  +-----------------+  +-----------------+
     |  RENDERER PID   |  |   GPU PROCESS   |  | NETWORK PROCESS |
     |  (chrome://...) |  |  (Compositor /  |  | (HTTP/3, TLS,   |
     |  - Blink Engine |  |   Vulkan / GL)  |  |  DNS Resolution)|
     |  - V8 JS Engine |  +-----------------+  +-----------------+
     |  - SANDBOXED    |
     +-----------------+
  • Browser Process: Privileged supervisor. Owns OS window handles, disk profile I/O, and raw network sockets.
  • Renderer Process: Sandboxed worker. Runs Blink (HTML/CSS layout) and V8 (JavaScript execution). Has zero raw disk or socket access.
  • Zygote Process: Pre-forked Linux template process used to spawn warm renderers instantly without full process startup overhead.
  • WebUI: Chromium's native pipeline for building internal browser pages using web standards backed by C++ controllers.

2. Chapter 2: The "Shim Pattern" & Rebase Sustainability

The 10-Line Rule: Large Chromium forks fail because they scatter modifications across core files. Obscure places >98% of its code in //chrome/browser/obscure/ and restricts core diffs to ≤10 lines of registration hooks.

3. Chapter 3: Git Workflow, Bundles & Bulletproof Rollback Safety

Chromium contains over 40 million lines of code. Reckless commands can destroy weeks of work. Obscure operates under a four-tier rollback safety model:

  1. Tier 1 (Git Revert): Creates inverse commits; non-destructive.
  2. Tier 2 (Patch Reversal): git apply --reverse cleanly removes a patch series.
  3. Tier 3 (Hard Reset to Immutable Tag): git reset --hard obscure-baseline-155.0.8059.39 guarantees 100% clean baseline recovery.
  4. Tier 4 (Git Bundles): git bundle create backups/obscure.bundle ... packages full commits into portable binary archives that restore identically even after hard resets.
Line Ending Invariant: We enforce *.patch -text in .gitattributes so Windows Git never converts LF to CRLF, preventing git am patch failures inside WSL2.

5. Chapter 5: Founder Defensible Knowledge (Investor & Architect Q&A)

Q: Why did you build Obscure on Chromium rather than building a browser engine from scratch?

Answer: Building a modern web rendering engine from scratch requires handling decades of CSS, HTML5, WebGL, WebGPU, JavaScript specifications, and thousands of video/audio codecs. Even Microsoft gave up on EdgeHTML to adopt Chromium. Chromium is the de facto engine of the modern web. Obscure's value is not reinventing the wheel—it's taking Chromium's world-class engine and giving developers unprecedented security isolation, workspace intelligence, and deep network/port visibility.

Q: How do you guarantee user privacy in Incognito windows?

Answer: We enforce privacy at the C++ configuration layer. In ObscureNewTabPageUIConfig::IsWebUIEnabled(), we check !profile->IsOffTheRecord(). In Incognito and Guest modes, this returns false, causing Chromium to fall back to its native private screens. Obscure UI and custom state never load inside private sessions.
